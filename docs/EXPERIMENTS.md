# Experiments

This document defines the experiment protocol. **Results are generated by
`scripts/make_report.py` into `docs/RESULTS.md`; no numbers are written by hand.**

## Research questions

Primary: can RL develop competitive Tetris strategies against established
algorithmic opponents under TETR.IO Season 2 mechanics?

Secondary: PPO vs Double DQN; opponent-aware observation; Season 2 B2B
charging/Surge; single- vs mixed-opponent training; reward shaping.

## Common protocol

* **Ruleset**: `tetrio_s2` (SRS+, 180°, Season 2 attack table, B2B charging +
  Surge, garbage tank/cancellation) unless a run explicitly ablates it.
* **Observation**: identical encoder for both algorithms (889 floats with
  opponent channels, 479 without). No future randomizer information.
* **Actions**: 80 placement actions (rotation × column × hold), masked.
* **Reward**: identical `RewardConfig` for both algorithms; every component is
  logged separately (`reward/clear`, `reward/attack`, `reward/defense`,
  `reward/board_penalty`, ...).
* **Curriculum**: survival (solo) → random opponent → heuristic opponent, with
  stage timesteps scaled to the run's total budget.
* **Seeds**: training seed 0 for the matrix; evaluation uses paired seeds with
  side swapping. Win rates use Wilson 95% intervals and report *n*.
* **Checkpoints**: periodic + best-by-eval + final. Best checkpoints are never
  overwritten.

## Experiments

### A. PPO vs Double DQN
`configs/ppo_main.json`, `configs/dqn_main.json` — same environment, observation,
action space, reward, curriculum and seeds. Metrics: sample efficiency, final
win rate vs random/heuristic (and the held-out beam-search opponent), lines
cleared, attack efficiency, garbage cancelled.

### B. Reward shaping ablation
`configs/ablation_no_board_penalty.json` removes the board-quality terms
(height/holes/bumpiness) while keeping clear/attack/terminal terms, compared with
the shaped main PPO run. Tests whether shaping helps or whether the agent learns
to exploit the penalty (early self-termination is a known failure mode).

### C. Single vs mixed opponents
`configs/single_heuristic.json` trains only against the heuristic; 
`configs/mixed_opponents.json` samples random/heuristic/search per episode, plus
`variant`: a parameterised in-repo opponent that resamples jittered heuristic
weights / evaluation noise / beam width / lookahead depth per episode
(`tetrisrl/agents/variants.py`). Variants are seeded, so mixed training and
replays stay reproducible.
Both are evaluated against all three, including the unseen opponent, to measure
generalisation.

### D. Opponent-observation ablation
`configs/ablation_no_opponent_obs.json` sets `include_opponent=false`, removing
the opponent board, heights, pending garbage and history channels (the encoder
shrinks from 889 to 479 features). Everything else is identical.

### E. Season 2 B2B charging / Surge
`configs/ablation_s1_ruleset.json` sets every curriculum stage to `tetrio_s1`
(classic B2B chaining, no Surge) with the same everything else. Compare the
frequency of difficult clears, B2B maintenance and Surge usage, and the resulting
attack strategy.

### F. Sample efficiency and convergence
Metric series are persisted per timestep; `docs/RESULTS.md` plots reward, win
rate, lines, and board metrics with moving averages.

### G. Generalisation to unseen opponents
Final checkpoints are evaluated against `search`, which is not used in the main
runs' training curriculum. Performance against `search` is reported separately
from the trained-against opponents.

## Evaluation procedure

`scripts/run_experiments.py --matrix evaluate --matches 40` evaluates each run's
best checkpoint against `random`, `heuristic`, and `search`:

* paired seeds (`seed + i`), half the matches on each side;
* match length limit 500 pieces;
* per-match records written to `results/evaluations/evaluation_summary.json`;
* win/loss/draw counts, lines, attack/min, attack efficiency, garbage cancelled,
  final height/holes, top-out rate, and Wilson intervals.

## Tournaments

`python -m tetrisrl tournament` runs a round robin (or `run_round_robin`) with
replay files per match and a CSV export. Replays include both boards, garbage and
attack events, and can be verified by re-simulation.

## Reproducibility

Exact commands are in `docs/REPRODUCIBILITY.md`. Each run's directory contains
its full configuration; the SQLite database contains every metric point and the
checkpoint index. Ablations differ only in the dimension named above.

## What is not claimed

* No statistical significance is claimed for differences whose confidence
  intervals overlap.
* Runs are short relative to the compute budget needed for strong play; the
  results characterise this budget, not an upper bound on the method.
* External engines are placement suggesters; Season 2 attack/charge/garbage is
  always computed by our arena. See `docs/BENCHMARKS.md`.


## Pretraining (behaviour cloning)

`mode: "pretrain"` collects demonstrations instead of running RL:

1. each epoch runs a mini round robin between the selected opponents with
   epoch-derived seeds (fresh games every epoch);
2. only the **winning side's** `(observation, action, mask)` trajectories are
   kept — losses and draws are discarded;
3. the PPO actor (or DQN Q-network) is trained with masked cross-entropy for
   the configured cloning passes.

Checkpoints are saved per epoch and can seed a later `continue` run. Outcomes:
`pretrain/dataset`, `pretrain/matches`, `pretrain/draws`, `pretrain/loss`,
`pretrain/updates`, plus periodic evaluation. Important caveat: this is
**imitation of the strongest selected opponent, not RL**, so it cannot exceed
the demonstrator's policy and inherits its action-space gaps (tucks/spins). It
is a warm start, not evidence about RL's competitive ceiling.
